# Утилитсервис — корпоративный сайт

Статический многостраничный сайт на Markdown и [Notepub](https://github.com/cookiespooky/notepub) с небольшим PHP-бэкендом для приёма заявок.

## Где размещён

| Площадка | Адрес | Назначение |
|---|---|---|
| Боевой сайт | https://utilityservice.ru | виртуальный хостинг reg.ru (ISPmanager), PHP-бэкенд работает |
| Превью | https://cookiespooky.github.io/util/ | GitHub Pages для согласования, PHP там нет |

Площадки отличаются только конфигурацией сборки. Все внутренние ссылки и пути к файлам Notepub подставляет **абсолютными** из `base_url`, поэтому сборка, сделанная с чужим конфигом, уводит посетителя на другую площадку — собирать нужно тем конфигом, куда выкладываете.

## Что внутри

- `content/` — тексты и структура страниц во frontmatter;
- `theme/templates/` — HTML-шаблоны и партиалы;
- `theme/assets/` — CSS, JavaScript, шрифт, логотипы, фотографии и логотипы клиентов;
- `api/` — PHP-бэкенд: приём заявок и определение города по IP;
- `deploy/htaccess` — конфигурация Apache для корня боевого сайта;
- `rules.yaml` — типы страниц, маршруты, коллекции, поиск и sitemap;
- `config.yaml` — сборка превью для GitHub Pages;
- `config.regru.yaml` — сборка боевого сайта;
- `config.dev.yaml` — локальный просмотр;
- `CONTENT-GLOSSARY.md` — обязательная терминология: чем «обезвреживание» отличается от «уничтожения» и «размещения»;
- `CONTENT-SPEC.md` — структура меню, формулировки CTA, поля формы и обязательная оговорка;
- `docs/` — карта страниц, контракт блоков и фиксация этапа 2.

## Как устроен контент

Страницы **описываются frontmatter'ом, а не текстом**: шаблон читает `hero_title`, `facts`, `process`, `faq` и остальные поля и собирает из них секции. Тело Markdown-файла — строка-заглушка, поясняющая это. Чтобы изменить страницу услуги, правят её frontmatter; чтобы добавить новую секцию — заводят поле в `fields.optional` внутри `rules.yaml` и ветку `{{- if .FM.<поле> }}` в шаблоне. Отсутствующее поле молча убирает секцию.

Контакты подразделений живут **только** во frontmatter страниц в `content/cities/`. Оттуда они расходятся в шапку, подвал, схему на главной, блок рядом с формой и в справочник для бэкенда `api/site-data.generated.json`, который пересобирается при каждой сборке. Своей копии телефонов ни в шаблонах, ни в JavaScript нет.

## Локальная работа

Нужен Go 1.22+ либо готовый `notepub` в `PATH`.

```bash
notepub serve --config ./config.dev.yaml --rules ./rules.yaml   # просмотр на :8080
./scripts/build.sh                                              # полная сборка в dist/
```

`build.sh` устанавливает зафиксированную версию Notepub, проверяет frontmatter, маршруты, wikilinks и Markdown, строит индекс, выгружает справочники для бэкенда, собирает сайт и проверяет результат. Конфиг и каталог сборки задаются переменными окружения:

```bash
CONFIG=./config.regru.yaml DIST=./dist-prod ./scripts/build.sh
```

**После правки шаблонов обязательно проверьте, что тема не рассыпалась.** Ошибка в одном шаблоне переводит *все* страницы на встроенный макет Notepub, при этом сборка сообщает об успехе:

```bash
grep -c 'np-shell' dist/index.html    # 0 — тема применилась, 1 — упала
```

## Выкладка

Боевой сайт:

```bash
REGRU_HOST=u3574260@server269.hosting.reg.ru ./scripts/upload-regru.sh
```

Скрипт собирает сайт с `config.regru.yaml`, отказывается выкладывать сборку, в которой остались адреса GitHub Pages, и заливает по rsync. `api/config.php` с паролем от почты и журнал заявок он не трогает. `DRY_RUN=1` показывает изменения, ничего не меняя.

Превью на GitHub Pages:

```bash
./scripts/deploy.sh "Сообщение коммита"
```

Коммитит фиксированный список путей и пушит; публикацию делает GitHub Actions.

## Бэкенд

`api/request.php` принимает заявку: сначала пишет её в журнал вне корня сайта, и только потом отправляет письмо — при недоступном SMTP обращение не теряется. Роботов отсеивают скрытое поле-приманка, отметка времени заполнения и ограничение частоты запросов. `api/city.php` отдаёт только ключ города, чтобы страницы остались статикой.

### Определение города

`api/city.php` возвращает только ключ подразделения, подстановку делает браузер. Источник данных — бесплатная база [SypexGeo](https://sypexgeo.net/) (лицензия BSD): читатель лежит в `api/lib/SxGeo.php`, сама база `SxGeoCity.dat` — в каталоге журнала заявок вне корня сайта. В репозиторий она не попадает: 37 МБ и регулярно обновляется.

База обновляется сама: на сервере стоит задача cron на 5-е число каждого месяца, отчёт пишется в `storage/sxgeo-update.log`. Скачивание идёт во временный файл, поэтому при обрыве связи на месте остаётся прежняя рабочая база. Посмотреть или снять задачу — `crontab -l` и `crontab -e`. Вручную то же самое:

```bash
cd ~/storage && curl -sSO https://sypexgeo.net/files/SxGeoCity_utf8.zip \
  && unzip -o -q SxGeoCity_utf8.zip && rm SxGeoCity_utf8.zip
```

Читатель — версия 2.2.3 от 2014 года, в ней поправлены обращения к строкам через фигурные скобки: этот синтаксис удалён в PHP 8. При замене файла с sypexgeo.net правку нужно повторить, иначе скрипт не запустится.

Определённый город никогда не подставляется молча — сайт спрашивает подтверждение. Сургут и Нягань лежат в одном округе и по IP различаются ненадёжно, поэтому вопрос посетителю обязателен.

`api/config.php` создаётся на сервере из `config.sample.php` и в репозиторий не попадает: в нём пароль почтового ящика. Форма отправляет заявку, только если в конфиге сборки задан `request_endpoint` — на превью его нет, и там форма показывает заглушку.

## Что вычитывает и утверждает заказчик

Юридические тексты, действующие лицензии и приложения к ним, количественные показатели компании, а также допустимость публикации названий клиентов, логотипов и отзывов. Неподтверждённые сведения на сайт не выкладываются.
