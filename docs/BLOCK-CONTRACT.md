# Контракт семантических блоков Markdown

## Назначение

Контракт отделяет содержание страницы от её сетки и оформления. Markdown хранит текст и семантику; шаблон выбирает HTML-компонент и визуальный вариант.

## Синтаксис блока

```md
<!-- block:hero -->

# Заголовок страницы

Лид страницы.

[Основное действие] [Вторичное действие]

<!-- /block -->
```

Имя блока состоит из латинских букв, цифр и дефиса. Один и тот же именованный блок может повторяться только тогда, когда шаблон явно допускает коллекцию.

## Синтаксис компонента

```md
<!-- component:request-form
variant: service
city: current
service: current
show_file: true
-->
```

Директива компонента не содержит HTML. Параметры задаются как `key: value`, по одному на строку.

## Поддерживаемые блоки

### `hero`

Ожидает:

- один `h1`;
- ноль или один лид-абзац;
- ноль, одну или две CTA-ссылки.

Параметры из frontmatter:

- `hero_variant`;
- `accent`;
- `visual`.

### `intro`

Обычный Markdown: абзацы, списки, ссылки, выделение. Не допускает вложенные компоненты со сложной сеткой.

### `services`

Ожидает список wikilinks на страницы типа `service` или декларацию `service-grid`.

### `process`

Ожидает нумерованный список. Каждый пункт становится этапом.

Допустимые варианты:

- `timeline`;
- `route`;
- `compact`.

### `requirements`

Ожидает маркированный список. Элементы могут быть сгруппированы под `h3`.

### `facts`

Ожидает список проверенных фактов. Числовые показатели должны иметь подтверждённый источник до публикации.

### `capabilities`

Ожидает список или группы с `h3`. Используется для производственной базы, оборудования и транспорта.

### `documents`

Ожидает ссылки на документы, wikilinks или декларацию коллекции.

### `cities`

Ожидает ссылки на страницы типа `city` или компонент карты.

### `faq`

Ожидает повторяющиеся пары:

```md
### Вопрос

Ответ.
```

### `cta`

Ожидает заголовок, краткое описание и одну или две ссылки.

### `request-form`

Используется только как компонентная декларация.


## Общие параметры компонентов

| Параметр | Значение |
|---|---|
| `variant` | Визуальный или функциональный вариант компонента |
| `source` | `current`, имя блока, коллекция или путь к данным |
| `limit` | Максимальное число элементов |
| `city` | `current`, `auto`, конкретный идентификатор |
| `service` | `current`, `select`, конкретный идентификатор |
| `compact` | Логическое значение для сокращённого режима |
| `show_*` | Явное включение необязательной возможности |

## Пример страницы услуги

```md
---
type: service
slug: medical-waste
title: Медицинские отходы
service_key: medical
hero_variant: service
process_variant: timeline
---

<!-- block:hero -->

# Медицинские отходы

Сбор, транспортирование и обезвреживание отходов медицинских организаций.

[Получить расчёт]

<!-- /block -->

<!-- block:intro -->

Редакционное описание услуги.

<!-- /block -->

<!-- block:requirements -->

## Что потребуется для расчёта

- класс отходов;
- объём;
- адрес;
- периодичность.

<!-- /block -->

<!-- block:process -->

## Как проходит работа

1. Уточняем сведения.
2. Проверяем возможность выполнения.
3. Согласовываем условия.
4. Выполняем работы.
5. Передаём документы.

<!-- /block -->

<!-- component:related-services
source: fm.related
-->

<!-- component:request-form
variant: service
city: current
service: current
show_file: true
-->
```

## Ошибки валидации

Сборка должна выдавать ошибку или предупреждение в следующих случаях:

- неизвестное имя блока;
- незакрытый блок;
- повтор уникального блока;
- несколько `h1` внутри hero;
- неизвестный компонент;
- неизвестный параметр компонента;
- ссылка на сущность неподходящего типа;
- обязательный блок отсутствует для типа страницы.

## Обратная совместимость

До внедрения парсера страница может содержать обычный Markdown. Шаблон выводит его в `.prose` как fallback. После миграции конкретного типа страницы семантические блоки становятся основным контрактом, а DOM-перестановки удаляются.
